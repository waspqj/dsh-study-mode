# 0.3.27 改版性能测试报告

测试时间：2026-11-06 23:20 — 2026-11-07 00:30（本机，Windows / Node 24 / DSH 运行时 0.2.2-rc.1）
测试对象：`dsh-study-preset`（开发副本）相对上一版的改动 —— **学习模式预设从 6 行补到 19 行**、
**删掉工具白名单**、**新增 `learn_enable_edit`**、**persona 允许解析工作区文件**。

所有脚本都在 `../.tools/` 下可复跑：

| 脚本 | 测什么 |
| --- | --- |
| `perf-kb-bench.mjs` | 插件热路径（检索/枚举/写入/提议）的延迟与输出体积 |
| `perf-store-io.mjs` | 存储层 I/O（冷启动/读/原子写/备份） |
| `perf-api-bench.mjs` | 真实宿主 `/kb/api/*` 各路由的延迟 |
| `perf-catalog-size.mjs` | 工具清单的体积（字符/token） |
| `perf-model-ab.mjs` | 模型 A/B 大电池（12 题 × 2 组 = 24 次真实调用） |
| `perf-longsession.mjs` | 长会话（同一会话 12 轮）的 token 增长与缓存命中 |
| `perf-stress.mjs` | 并发压测 |
| `perf-ui-bench.mjs` | 面板渲染性能（真 React 18 + jsdom + 真实库） |

---

## 一句话结论

**工具从 32 个涨到 75 个，检索流程没被带偏（首工具正确率 10/12 → 11/12），
延迟没退化（平均 +9.5%，p95 反而 -12%），代价是每请求多 ≈ 9,900 token 的工具 schema。**
插件自己的热路径全部在**毫秒级**，面板首屏 **131ms**，并发天花板 ≈ **40 检索/秒**。

## 9. 新功能验证：`learn_enable_edit` 模型会不会自己挂

真实模型跑三题（B 组清单，75 个工具）：

| 题目 | 实际调用序列 | 结果 |
| --- | --- | --- |
| 「把间隙锁那张卡的标题改成『间隙锁详解』」 | `learn_enable_edit → learn_search → learn_topics → learn_entries → ops_discover_tools → …` | ✔ 先挂上了 ✓；后半段是**测试桩的假象**（桩里没有真的把 `learn_update` 加进清单 ✓✗，真实宿主会加 ✓✓） |
| 「删掉知识库里那条『间隙锁(Gap Lock)』」 | **`learn_enable_edit → learn_entries → learn_delete`** | ✔✔✔ **挂上后真的改/删成功了** ✓✓（`learn_delete` 只有挂上后才有 ✓ ✓✓） |
| 「间隙锁是什么？」 | `learn_search → learn_search → learn_entries → learn_propose → learn_entries` | ✔ 普通提问**没碰**编辑工具 ✓✓ |

⇒ **「默认关、提出来了再主动调用」这条需求成立** ✓✓：模型在需要时自己调 `learn_enable_edit` ✓✓，
不需要时那 900 token 一个都不花 ✓✓。

## 结论与建议

1. **工具变多没有把模型带偏** ✓✓：首工具正确率不降反升（10→11 ✓），检索顺序完全一致 ✓。
2. **延迟没有退化** ✓✓：平均 +9.5%（在模型生成时间的波动范围内 ✓），p95 反而更低 ✓。
3. **要付的代价是每请求 ≈ +9,900 token 的固定前缀** ✓✓ —— DeepSeek 按缓存读价 ≈ **0.05 分/轮** ✓，
   MiniMax 预付套餐 **边际为 0** ✓ ✓。
4. **最占地方的不是我们的工具** ✓✓ —— 是浏览器那套 `bsk_*`（10.3k = 36% ✓✓）；
   我们的 `learn_*` 六个才 2,425 token ✓✓。
5. **插件自己不是瓶颈** ✓✓：检索 p50 ≈ 30ms ✓、写入 p50 ≈ 28ms ✓、面板首屏 131ms ✓、
   并发天花板 40 检索/秒 ✓。
6. **唯一要注意的**：打开 AI 重排后，检索会多一次模型调用（2–10s ✓）✓ —— 现在线上没有走这条路 ✓ ✓。
